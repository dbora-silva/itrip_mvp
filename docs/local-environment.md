# Local environment (provisional — Phase 3)

This is a provisional reference for the Docker + Supabase local setup introduced in Phase 3.
It will be superseded by the full README in Phase 11.

## Two moving pieces, started separately

1. **Supabase local stack** — owned entirely by the Supabase CLI (`supabase start` /
   `supabase stop`). Runs Postgres, Auth (GoTrue), PostgREST, Studio, Mailpit, etc. in its
   own Docker containers, on its own Docker network. Nothing in this repository's
   `docker-compose.yml` recreates or references those containers by name — see
   "Why the app container doesn't join Supabase's Docker network" below.
2. **The Next.js application** — either run directly on the host (`npm run dev`, fastest
   inner loop) or containerized via `docker compose` (closer to how it will actually run in
   production, useful for validating the Dockerfile itself).

Both can point at either a **local** Supabase stack or a **hosted** Supabase project — this
is controlled entirely by environment variables, not by code branches (see
[Environment variables](#environment-variables)).

## Commands

| Command                   | What it does                                                                               |
| ------------------------- | ------------------------------------------------------------------------------------------ |
| `npm run supabase:start`  | Starts the local Supabase stack (first run pulls Docker images; can take several minutes). |
| `npm run supabase:status` | Prints the local stack's URLs and keys.                                                    |
| `npm run supabase:stop`   | Stops the local Supabase stack.                                                            |
| `npm run db:reset`        | Re-applies all migrations and `supabase/seed.sql` from scratch (`supabase db reset`).      |
| `npm run docker:build`    | Builds the application's Docker image.                                                     |
| `npm run docker:up`       | Builds (if needed) and starts the application container.                                   |
| `npm run docker:down`     | Stops and removes the application container.                                               |

## Why the app container doesn't join Supabase's Docker network

Supabase CLI creates and names its own Docker network and containers internally. That
naming is an implementation detail of the CLI, not a documented, stable contract — relying
on it (e.g. `supabase_kong_itrip_mvp:8000`) would silently break on a CLI upgrade.

Instead, the app container reaches the Supabase API gateway the same way any external
client would: through the port Supabase publishes to the **host** (`54321`), using Docker
Desktop's built-in `host.docker.internal` DNS entry. `extra_hosts: host.docker.internal:host-gateway`
in `docker-compose.yml` makes the same mechanism work on native Linux Docker Engine, where
`host.docker.internal` isn't automatic.

This means the application **never talks to Postgres directly** and **never depends on any
Supabase-internal container name** — it only depends on one published port, the same
contract Supabase documents for any external tool connecting to the local stack.

## Environment variables

See `.env.example` for the authoritative, commented list. Summary:

| Variable                                               | Where it's used                           | Sensitivity                                         |
| ------------------------------------------------------ | ----------------------------------------- | --------------------------------------------------- |
| `NEXT_PUBLIC_SUPABASE_URL`                             | Browser and server (fallback)             | Public                                              |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY`                        | Browser and server                        | Public                                              |
| `SUPABASE_URL` (server-only, no `NEXT_PUBLIC_` prefix) | Server only, inside the app container     | Not secret, but must never reach the browser bundle |
| `SUPABASE_SERVICE_ROLE_KEY`                            | **Not used anywhere in this application** | Secret — do not add it                              |

`NEXT_PUBLIC_SUPABASE_URL` is what the _browser_ uses, so it must always be a URL the
browser can resolve (`http://127.0.0.1:54321` locally, or the hosted project URL).
`SUPABASE_URL` exists only to give server-side code (running inside the Docker container) a
different, container-resolvable address (`http://host.docker.internal:54321`) without ever
touching the public variable. `docker-compose.yml` sets it automatically; it is not needed
when running `npm run dev` directly on the host, and not needed against a hosted project
(its URL is reachable the same way from anywhere).

### `NEXT_PUBLIC_*` variables are baked in at build time

Next.js inlines every `NEXT_PUBLIC_*` variable into the JavaScript bundle **at build time**,
not at container start time. There is no client-side Supabase usage yet in this phase (only
the server-side readiness check reads these variables), so this has no effect today. It
will matter once a browser-side Supabase client exists (a later phase): switching
`NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` between local and hosted values
will require **rebuilding the Docker image** (`npm run docker:build`), not just restarting
the container with different environment variables — restarting alone would only change
what server-side code sees. Never pass real keys as build arguments or `ARG`/`ENV` layers
baked into the image; they belong in `.env.local` / the container's runtime environment.

### Local Supabase vs. hosted Supabase

Switching is just a matter of which values `.env.local` holds:

- **Local**: `NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:54321`, anon key from
  `npm run supabase:status`.
- **Hosted**: `NEXT_PUBLIC_SUPABASE_URL` = your project's URL (Project Settings > API),
  anon key = the anon/public key from the same page. Never request or paste the
  service-role key anywhere in this project.

## Liveness vs. readiness

- **Liveness** — `GET /api/health`. Always returns `{"status":"ok"}` if the Next.js process
  is up. Does not touch any external dependency. This is what the Dockerfile's
  `HEALTHCHECK` and `docker-compose.yml`'s `healthcheck` poll — Docker restarts the
  container if this stops responding.
- **Readiness** — `GET /api/ready`. Performs a live network call to the Supabase API
  gateway's `/auth/v1/health` endpoint (resolving `SUPABASE_URL` first, falling back to
  `NEXT_PUBLIC_SUPABASE_URL`). Returns `503` if the gateway is unreachable within 3s, `200`
  with the gateway's own HTTP status otherwise. This is intentionally **not** wired into
  Docker's single built-in `HEALTHCHECK` — liveness and readiness answer different
  questions, and only liveness should cause Docker to restart the container. Readiness is
  meant to be polled externally (by a human, a script, or later CI) before relying on
  Supabase-dependent behavior.

## Known limitation: regenerating `package-lock.json` across platforms

`npm install`, run on Windows, does **not** reliably preserve optional-dependency entries
that only apply on Linux (the Docker image's platform), and vice versa — each platform's
`npm install` prunes what its own platform doesn't need. Concretely: `npm ci` inside the
`node:24-alpine` build stage failed with `Missing: @emnapi/runtime@1.11.3 from lock file`
after a plain Windows-side `npm install`, because those entries are needed for the
WASM/emnapi fallback path on Linux/musl but not on Windows.

**Rule going forward:** only ever run `npm install` (which can rewrite `package-lock.json`)
inside a Linux container matching the Dockerfile's base image, e.g.:

```sh
docker run --rm -v "<absolute-project-path>:/app" -w /app node:24-alpine \
  sh -c "apk add --no-cache libc6-compat && npm install"
```

For everyday local installs on the host (Windows), use `npm ci` — it installs from the
lockfile exactly as committed, for whichever packages apply to the host platform, and never
rewrites it.

## First-run walkthrough

```sh
npm run supabase:start      # starts local Supabase (first run pulls images)
npm run supabase:status     # copy the anon key into .env.local
cp .env.example .env.local  # then edit it
npm run docker:up           # builds and starts the app container
curl http://localhost:3000/api/health   # liveness
curl http://localhost:3000/api/ready    # readiness (reaches Supabase via host.docker.internal)
```
